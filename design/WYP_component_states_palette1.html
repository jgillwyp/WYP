Component states — palette 1

One reference for every control state, so a screen mockup is only needed when the layout differs, not when a single control changes state. Values here are copied verbatim from app/globals.css; if the two ever disagree, globals.css wins.

Buttons

AVAILABILITY IS NOT EMPHASIS

.btn — primary (§6.1)

The main action on the screen. One per band.

.btn-secondary (§6.11)

Available, deliberately not the main action.

.btn-quiet (§6.16)

Global action that must stay reachable without competing.

.is-locked (§6.17, PROPOSED)

Not available because of the request’s tier. Inert, not lower emphasis.

Locked is a different axis from emphasis. Secondary and quiet both mean “you may do this.” Locked means you may not. It never borrows their styling.

Always pair a locked control with adjacent text saying why. The control shows that it is locked; the note says what would unlock it.

Use aria-disabled="true", never disabled. A disabled control leaves the tab order and screen readers skip it, so the person who most needs the explanation never reaches it. Block the action in the handler instead.

The padlock is required. Grey alone reads as “broken” or “still loading” as easily as “not available to you”.

It is a courtesy, not a control. The database refuses the write regardless. A locked button that is bypassed must still fail server-side.

When a variant screen is warranted

Control state → this page. A button that is locked, a field that is read-only, a chip that is gated. The layout is unchanged, so a second screen file would duplicate everything to show one difference — and then drift.

Layout or flow difference → its own screen file. An empty state, a modal or dialog, a first-run variant that removes actions, a screen whose sections change. These cannot be read off a component gallery.

Rule of thumb: if you can describe the difference as “that control is in state X”, it belongs here. If you have to describe it as “the screen shows something else”, it needs a file.
